## HTTP request and response

> **In short**: HTTP is a stateless request / response protocol: the client sends a method, a URL, headers and an optional body; the server answers with a status code, headers and an optional body. Stateless means each request carries everything needed (cookie, token): the server keeps no link between two requests by itself.

```text
POST /api/orders HTTP/1.1                 HTTP/1.1 201 Created
Host: shop.example.com                    Location: /api/orders/42
Content-Type: application/json            Content-Type: application/json
Authorization: Bearer eyJhbGci...
                                          {"id": 42, "status": "PENDING"}
{"customer": "alice", "total": 100}
```

- Request line: method + path (+ query string `?status=PAID`); response line: status code + reason.
- Headers: metadata (content type, authentication, caching, cookies); the body: the data (JSON, form, file).
- Sessions, login state and shopping carts are built on top of it, with cookies or tokens sent on every request.

## HTTP methods: safe and idempotent

> **In short**: `GET` reads, `POST` creates or triggers an action, `PUT` replaces a resource, `PATCH` modifies part of it, `DELETE` removes it. A **safe** method doesn't change anything on the server (`GET`, `HEAD`, `OPTIONS`); an **idempotent** one gives the same result whether it's called once or several times (`GET`, `PUT`, `DELETE`, but not `POST`), which makes it safe to retry.

| Method | Use | Safe | Idempotent | Body |
|---|---|---|---|---|
| `GET` | read a resource | yes | yes | no |
| `HEAD` | like `GET`, headers only | yes | yes | no |
| `OPTIONS` | allowed methods, CORS preflight | yes | yes | no |
| `POST` | create a resource, trigger an action | no | **no** | yes |
| `PUT` | replace a resource entirely (or create it at a known URL) | no | yes | yes |
| `PATCH` | partial update | no | not guaranteed | yes |
| `DELETE` | delete a resource | no | yes | rarely |

- **Idempotent** doesn't mean same response: a second `DELETE /orders/42` may return `404`, but the state of the server is the same (the order is deleted).
- Why it matters: a client, a proxy or a retry mechanism can safely resend an idempotent request after a timeout; resending a `POST` may create a duplicate order.
- Making a `POST` retryable: an `Idempotency-Key` header (a UUID generated by the client), stored by the server, which returns the first result when the same key comes back.
- A `GET` must never modify data: it can be prefetched, cached, or triggered by a link (CSRF, see [Security](SECURITY.md)).

## HTTP status codes

> **In short**: `2xx` success, `3xx` redirection, `4xx` client error (the request is wrong, retrying it unchanged won't help), `5xx` server error. The ones to know: `200`, `201`, `204`, `301` / `302`, `304`, `400`, `401` (not authenticated), `403` (not allowed), `404`, `409`, `422`, `429`, `500`, `502`, `503`.

| Code | Meaning | Typical case |
|---|---|---|
| `200 OK` | success with a body | `GET`, `PUT` returning the resource |
| `201 Created` | resource created, `Location` header with its URL | `POST /orders` |
| `204 No Content` | success without body | `DELETE`, `PUT` without returned resource |
| `301` / `308` | permanent redirect (`308` keeps the method) | URL moved, HTTP → HTTPS |
| `302` / `307` | temporary redirect (`307` keeps the method) | redirect to a login page |
| `304 Not Modified` | cached version still valid (see conditional requests below) | `If-None-Match` |
| `400 Bad Request` | malformed request | invalid JSON, missing parameter, validation error |
| `401 Unauthorized` | **not authenticated**: missing or invalid credentials | no token, expired token |
| `403 Forbidden` | authenticated but **not allowed** | a user calling an admin endpoint |
| `404 Not Found` | resource doesn't exist (or hidden) | `GET /orders/999` |
| `405 Method Not Allowed` | method not supported on this URL | `DELETE` on a read-only resource |
| `409 Conflict` | conflict with the current state | duplicate, optimistic locking failure |
| `412 Precondition Failed` | `If-Match` condition failed | resource modified meanwhile |
| `415` / `406` | unsupported request `Content-Type` / no acceptable response type | XML sent to a JSON API |
| `422 Unprocessable Content` | well-formed but semantically invalid | business rule violated (some APIs use `400`) |
| `429 Too Many Requests` | rate limit exceeded, with `Retry-After` | API quota |
| `500 Internal Server Error` | unexpected server error | unhandled exception |
| `502` / `504` | the gateway / proxy got an invalid response / no response in time from the upstream server | backend down or too slow behind a load balancer |
| `503 Service Unavailable` | temporarily unavailable, `Retry-After` | maintenance, overload |

- `401` vs `403`: the name `Unauthorized` is misleading, it means unauthenticated; authenticating again can fix a `401`, not a `403`.
- Retrying: `5xx`, `429` and network errors are worth retrying (with backoff, idempotent requests only); `4xx` aren't.
- Error bodies: a standard format, `application/problem+json` (RFC 9457, `ProblemDetail` in Spring).

## REST API design

> **In short**: REST models the API as **resources** identified by URLs (nouns, plural: `/orders/42`), manipulated with the HTTP methods (the verbs) and represented as JSON, with meaningful status codes. Stateless: each request carries its authentication. Filtering, sorting and pagination go in the query string, and breaking changes need a new API version.

| Action | Request | Response |
|---|---|---|
| list | `GET /orders?status=PAID&page=0&size=20&sort=createdAt,desc` | `200` + list |
| read | `GET /orders/42` | `200`, or `404` |
| create | `POST /orders` | `201` + `Location: /orders/42` |
| replace / update | `PUT /orders/42` / `PATCH /orders/42` | `200` or `204` |
| delete | `DELETE /orders/42` | `204` |
| sub-resource | `GET /customers/7/orders` | `200` |
| action that isn't CRUD | `POST /orders/42/cancel` | `200` or `204` |

- Nouns, not verbs: `POST /orders`, not `POST /createOrder`; the method is the verb.
- **Versioning**: in the path (`/api/v2/orders`), a header, or the media type (`Accept: application/vnd.shop.v2+json`); Spring Framework 7 supports all of them (`version` attribute of the mappings).
- **Backward compatibility**: adding an optional field is safe; renaming or removing a field, changing a type or a status code breaks the clients.
- **Richardson maturity model**: level 0 (one URL, RPC), 1 (resources), 2 (resources + HTTP methods and status codes, what "REST API" usually means), 3 (HATEOAS: responses contain links to the possible next actions, rarely used).
- Documentation: OpenAPI (Swagger), generated with springdoc-openapi in Spring.

## Important headers and cookies

> **In short**: `Content-Type` describes the body sent, `Accept` the formats the client wants, `Authorization` carries the credentials (`Bearer <token>`), `Location` points to a created resource. Cookies are set by the server with `Set-Cookie` and sent back automatically by the browser; `HttpOnly`, `Secure` and `SameSite` are the attributes that protect them.

| Header | Direction | Role |
|---|---|---|
| `Content-Type: application/json` | both | format of the body |
| `Accept: application/json` | request | expected response formats (content negotiation) |
| `Authorization: Bearer <jwt>` / `Basic <base64>` | request | credentials |
| `Cookie` / `Set-Cookie` | request / response | cookies sent back / set by the server |
| `Location` | response | URL of the created resource (`201`) or redirect target (`3xx`) |
| `Cache-Control`, `ETag`, `If-None-Match` | both | caching (see below) |
| `Origin`, `Access-Control-Allow-Origin` | request / response | CORS (see below) |
| `X-Request-Id` / `traceparent` | request | correlation id / distributed tracing |
| `Retry-After` | response | when to retry (`429`, `503`) |

```text
Set-Cookie: SESSION=a1b2c3; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1800
```

| Cookie attribute | Effect |
|---|---|
| `HttpOnly` | not readable by JavaScript (`document.cookie`): protects against theft by XSS |
| `Secure` | sent over HTTPS only |
| `SameSite=Strict` / `Lax` / `None` | not sent on cross-site requests / only on top-level `GET` navigations / always (requires `Secure`): protects against CSRF |
| `Max-Age` / `Expires` | persistent cookie; without them, deleted when the browser closes |
| `Domain`, `Path` | where the cookie is sent |

`Lax` vs `Strict` for a session cookie: with `Strict`, a user arriving from a link in an email or another site looks logged out on the first page, since the cookie isn't sent on that navigation. Hence `Lax` for the session cookie, `Strict` for cookies only used by the application's own `fetch` calls (e.g. a refresh token cookie).

## HTTP caching: Cache-Control

> **In short**: `Cache-Control` tells clients and proxies whether and how long a response can be reused: `max-age` (reuse without asking), `no-cache` (store but revalidate each time), `no-store` (never store), `private` / `public`, `immutable`. Typical SPA setup: `index.html` with `no-cache`, hashed bundles cached for a year.

The server tells the client (browser, proxy, CDN) whether and how long a response can be reused, with the `Cache-Control` response header:

```
Cache-Control: max-age=3600
```

- **`max-age=N`**: the response is fresh for N seconds. During that time, the client reuses it **without any request** to the server.
- **`no-cache`**: can be stored, but must be revalidated with the server before each reuse (see conditional requests below). Misleading name: it doesn't mean "don't cache".
- **`no-store`**: never stored anywhere. For sensitive data (banking pages, personal data).
- **`private`** / **`public`**: only the browser can store it (user-specific response), or shared caches too (proxy, CDN).
- **`immutable`**: the content never changes, no revalidation even on reload. Typical for hashed static files (`main.3f9a2c.js`), with a long `max-age`.

Typical setup for an Angular app: `index.html` with `no-cache` (always the latest version, which references the new hashed bundles), hashed bundles with `max-age=31536000, immutable`.

## Conditional requests: ETag and Last-Modified

> **In short**: To revalidate a cached response, the client sends back the validator it received (`If-None-Match` with the `ETag`, or `If-Modified-Since` with `Last-Modified`); if nothing changed, the server answers `304 Not Modified` without a body. `If-Match` on a write gives optimistic locking (`412` if the resource changed).

Once a cached response is stale (or with `no-cache`), the client doesn't download it again blindly: it asks the server whether it changed. If not, the server answers **`304 Not Modified`** with no body, and the client reuses its copy. Saves bandwidth, not the round trip.

Two mechanisms, the server sends a validator with the response and the client sends it back:

| Response header (server)                       | Request header (client)          | Compares                     |
| ---------------------------------------------- | -------------------------------- | ---------------------------- |
| `ETag: "a1b2c3"` (version id, e.g. a hash)     | `If-None-Match: "a1b2c3"`        | the ETag, exact match        |
| `Last-Modified: Tue, 21 Oct 2026 10:00:00 GMT` | `If-Modified-Since: <same date>` | the date, 1-second precision |

```
GET /api/books/42                    →  200 OK
                                        ETag: "v7"
                                        Cache-Control: no-cache
                                        { ...body... }

GET /api/books/42                    →  304 Not Modified    (unchanged, no body)
If-None-Match: "v7"

GET /api/books/42                    →  200 OK               (changed: new body, new ETag)
If-None-Match: "v7"                     ETag: "v8"
```

- `ETag` is more precise (no date granularity issue, works for content not tied to a file date) and takes precedence when both are sent.
- In Spring: `ShallowEtagHeaderFilter` computes an ETag from the response body hash (saves bandwidth, but the server still builds the response), or set it explicitly with `ResponseEntity.ok().eTag("\"v7\"").body(book)` and check `WebRequest.checkNotModified(etag)` to skip the work.
- Related, for writes: `If-Match: "v7"` on a `PUT` makes the server reject the update with `412 Precondition Failed` if the resource changed meanwhile (optimistic locking, like Hibernate's `@Version`).

## CORS

> **In short**: The browser's **same-origin policy** prevents a page from reading the responses of another origin (scheme + host + port). CORS lets the server allow some origins with `Access-Control-Allow-*` headers; for non-simple requests (JSON body, `Authorization` header, `PUT` / `DELETE`), the browser first sends a preflight `OPTIONS` request. It's a browser protection: it doesn't secure the API against other clients.

```text
OPTIONS /api/orders                          (preflight, sent by the browser)
Origin: http://localhost:4200
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

204 No Content
Access-Control-Allow-Origin: http://localhost:4200
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 3600                 (preflight cached for 1 hour)
```

- Same origin = same scheme, host and port: `http://localhost:4200` and `http://localhost:8080` are different origins.
- **Simple requests** (`GET` / `POST` with a form content type and no custom header) skip the preflight, but the response is still blocked if the origin isn't allowed.
- Cookies or credentials: the client sets `withCredentials`, the server answers `Access-Control-Allow-Credentials: true` with an explicit origin (not `*`).
- CORS isn't security for the API: `curl` or another server ignores it. It only stops a malicious page from reading responses with the user's browser.
- In development, an Angular proxy (`proxy.conf.json`) avoids CORS: the front-end and the API are served from the same origin. In Spring, CORS is configured in Spring Security (see [Spring Security](../back-end/spring/SPRING_SECURITY.md)).

## HTTPS and TLS

> **In short**: HTTPS is HTTP over TLS: the connection is encrypted (confidentiality), protected against modification (integrity), and the server proves its identity with a certificate signed by a trusted certificate authority (authentication). The TLS handshake agrees on keys with asymmetric cryptography, then the data is encrypted with fast symmetric keys.

1. The client connects and sends the TLS versions and algorithms it supports.
2. The server answers with its **certificate** (its public key, its domain, signed by a certificate authority).
3. The client checks the certificate: signed by a trusted authority, not expired, matching the domain.
4. Both sides derive shared session keys (Diffie-Hellman key exchange), and the rest of the connection is encrypted with them (AES).

- TLS 1.3 (current version): a single round trip for the handshake, obsolete algorithms removed; TLS 1.0 / 1.1 are deprecated.
- **HSTS** (`Strict-Transport-Security: max-age=31536000`): the browser only uses HTTPS for the domain, even if the user types `http://`, which prevents downgrade attacks.
- Certificates: free and automated with Let's Encrypt (ACME); internally, often terminated at the load balancer or ingress, with plain HTTP or mTLS behind it.
- **mTLS** (mutual TLS): the client also presents a certificate; used between services.

## HTTP/1.1 vs HTTP/2 vs HTTP/3

> **In short**: HTTP/1.1 sends one request at a time per connection, so browsers open several connections. HTTP/2 multiplexes many requests over one TCP connection, in binary frames with compressed headers. HTTP/3 runs over QUIC (UDP), which avoids TCP's head-of-line blocking and connects faster. The semantics (methods, headers, status codes) stay the same.

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| Transport | TCP | TCP | QUIC (over UDP), TLS 1.3 built in |
| Requests per connection | one at a time (keep-alive, ~6 connections per domain) | many in parallel (multiplexing) | many in parallel |
| Format | text | binary frames | binary frames |
| Headers | sent in full every time | compressed (HPACK) | compressed (QPACK) |
| Head-of-line blocking | per connection | at the TCP level: a lost packet blocks all streams | none: streams are independent |

- Consequences: with HTTP/2, the HTTP/1.1 optimizations (bundling everything in one file, domain sharding) matter less.
- In Spring Boot: `server.http2.enabled=true`; often handled by the load balancer or CDN in front of the application.

## Real-time: polling, SSE and WebSocket

> **In short**: To push data from the server: polling (the client asks regularly), long polling (the server holds the request until there's data), Server-Sent Events (a long-lived HTTP response streaming events from the server to the client), or WebSocket (a bidirectional connection, upgraded from HTTP). SSE is enough for notifications; WebSocket for two-way interaction (chat, collaboration, games).

| | Polling | SSE | WebSocket |
|---|---|---|---|
| Direction | client → server, repeated | server → client | both |
| Protocol | plain HTTP requests | HTTP (`text/event-stream`) | `ws://` / `wss://`, after an HTTP `Upgrade` |
| Reconnection | n/a | automatic (`EventSource`) | to implement |
| Use | simple, low frequency | notifications, progress, live feeds | chat, collaborative editing, games |

- SSE in Spring MVC: return an `SseEmitter`, or a `Flux<ServerSentEvent<?>>` with WebFlux.
- **Several instances**: the client's connection is held in memory by one instance, but the event may happen on another one (a message from another user, a Kafka message, a scheduled job, a webhook). The event is published to a shared channel that every instance listens to (Redis pub/sub, Kafka with one consumer group per instance, a STOMP broker relay), and the instance holding the connection forwards it.
- Sticky sessions (the load balancer always sends a client to the same instance, with a cookie or an IP hash) don't solve it: they route the client's own requests, not events coming from elsewhere.
