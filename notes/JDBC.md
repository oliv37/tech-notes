## JDBC basics: SELECT, INSERT, UPDATE, DELETE

Always use a `PreparedStatement` with `?` parameters, never string concatenation: the values are sent separately from the SQL, which prevents SQL injection. Resources (`Connection`, `PreparedStatement`, `ResultSet`) are closed with try-with-resources; with a pool, closing the connection returns it to the pool.

**SELECT**: `executeQuery()` returns a `ResultSet`, a cursor read row by row with `next()`.

```java
String sql = "SELECT id, title FROM book WHERE author_id = ?";

try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement(sql)) {
  statement.setLong(1, authorId);

  try (ResultSet rs = statement.executeQuery()) {
    List<Book> books = new ArrayList<>();
    while (rs.next()) {
      books.add(new Book(rs.getLong("id"), rs.getString("title")));
    }
  }
}
```

**INSERT**: `executeUpdate()` returns the number of inserted rows. To get the id generated by the database, ask for generated keys (or use `RETURNING id` with `executeQuery()` in PostgreSQL).

```java
String sql = "INSERT INTO book (title, author_id) VALUES (?, ?)";

try (PreparedStatement statement = connection.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
  statement.setString(1, "Dune");
  statement.setLong(2, authorId);
  statement.executeUpdate();

  try (ResultSet keys = statement.getGeneratedKeys()) {
    keys.next();
    long id = keys.getLong("id");
  }
}
```

**UPDATE / DELETE**: same `executeUpdate()`, which returns the number of affected rows (`0` if nothing matched, often worth checking).

```java
try (PreparedStatement statement = connection.prepareStatement(
    "UPDATE book SET title = ? WHERE id = ?")) {
  statement.setString(1, "Dune Messiah");
  statement.setLong(2, bookId);
  int updated = statement.executeUpdate();
  if (updated == 0) throw new BookNotFoundException(bookId);
}

try (PreparedStatement statement = connection.prepareStatement("DELETE FROM book WHERE id = ?")) {
  statement.setLong(1, bookId);
  int deleted = statement.executeUpdate();
}
```

`executeUpdate()` is **synchronous**: the driver sends the statement and waits for the server's answer before returning, one network round trip per call. Unlike Hibernate, where `persist()` or modifying an entity sends nothing until the flush. But executed doesn't mean committed: with auto-commit off (see below), the change stays invisible to other connections (PostgreSQL's default isolation is `READ COMMITTED`), and the modified rows stay **locked** until `commit()` / `rollback()`, blocking other transactions writing the same rows. Hence short transactions.

Exceptions: `addBatch()` only queues the statement until `executeBatch()` (see batching below). And `executeQuery()` sends the query right away, but pgJDBC loads the **whole result into memory** before returning by default; to stream a large result by chunks, disable auto-commit and set `statement.setFetchSize(500)`: the driver then uses a server-side cursor.

## JDBC auto-commit, transactions and read-only

By default, a JDBC `Connection` is in **auto-commit** mode: each statement is its own transaction, committed as soon as it's executed. To group several statements in a single transaction (all or nothing), auto-commit is disabled on the connection, and the transaction ends with `commit()` or `rollback()`:

```java
connection.setAutoCommit(false); // the transaction starts with the first statement
try {
  statement.executeUpdate("UPDATE account SET balance = balance - 100 WHERE id = 1");
  statement.executeUpdate("UPDATE account SET balance = balance + 100 WHERE id = 2");
  connection.commit();   // both...
} catch (SQLException e) {
  connection.rollback(); // ...or none
  throw e;
}
```

Calling `setAutoCommit(true)` in the middle of a transaction commits it.

JDBC has no `begin()` method: the driver translates the auto-commit mode into SQL. With PostgreSQL (pgJDBC):

```java
connection.setAutoCommit(false);               // nothing sent: the driver only sets a flag
statement.executeUpdate("UPDATE account ..."); // BEGIN + UPDATE
statement.executeUpdate("UPDATE account ..."); // UPDATE (already in the transaction)
connection.commit();                           // COMMIT
statement.executeQuery("SELECT ...");          // BEGIN + SELECT: a new transaction starts
```

- The `BEGIN` is sent lazily, with the first statement after `setAutoCommit(false)` or after each `commit()` / `rollback()`, in the same network message (no extra round trip).
- In auto-commit mode, no `BEGIN` is sent: PostgreSQL runs each statement in its own implicit transaction.
- With `connection.setReadOnly(true)`, the driver sends `BEGIN READ ONLY` instead: any write then fails with `cannot execute UPDATE in a read-only transaction`.
- To see it: `log_statement = 'all'` in PostgreSQL logs the `BEGIN` / `COMMIT` around the statements.

In Spring, `@Transactional` does this for you: the transaction manager calls `setAutoCommit(false)` (and `setReadOnly(true)` with `readOnly = true`, plus the isolation level if set) at the start, commits or rolls back at the end, then **restores** what it changed. Spring can't rely on the pool to reset the connection: there may be no pool (`SingleConnectionDataSource` reuses the same connection), and not every pool does it. It only restores what it changed, and HikariCP only resets the properties actually modified when a connection comes back, so the double reset costs almost nothing. Without `@Transactional`, a `JdbcTemplate` runs in auto-commit, each statement committed separately.

The same pattern by hand, simplified from what Spring's `DataSourceTransactionManager` does:

```java
public <T> T inTransaction(DataSource dataSource, SqlFunction<Connection, T> work) throws SQLException {
  try (Connection connection = dataSource.getConnection()) {
    boolean previousAutoCommit = connection.getAutoCommit();
    if (previousAutoCommit) {
      connection.setAutoCommit(false); // only switch if needed
    }
    try {
      T result = work.apply(connection);
      connection.commit();
      return result;
    } catch (SQLException | RuntimeException e) {
      connection.rollback();
      throw e;
    } finally {
      if (previousAutoCommit) {
        connection.setAutoCommit(true); // restore only what was changed
      }
    }
  }
}

@FunctionalInterface
interface SqlFunction<A, R> {
  R apply(A arg) throws SQLException;
}

// usage
long bookId = inTransaction(dataSource, connection -> insertBook(connection, "Dune"));
```

The restore happens in `finally`, after the commit or the rollback (restoring before the commit would commit, since `setAutoCommit(true)` commits the current transaction).

- **`readOnly = true` with JPA**: also puts the Hibernate session in read-only mode, no flush (`FlushMode.MANUAL`) and no snapshots for dirty checking, which saves memory and CPU on large reads. This is why Spring Data's `SimpleJpaRepository` is `@Transactional(readOnly = true)` at class level, write methods overriding it with `@Transactional`.
- **Optimization with Hibernate**: `spring.datasource.hikari.auto-commit=false` and `spring.jpa.properties.hibernate.connection.provider_disables_autocommit=true`. Connections are already in the right mode, so nothing to switch and restore, and Hibernate can delay acquiring the connection until the first SQL statement.
- **Routing reads to a replica**: an `AbstractRoutingDataSource` can choose the database with `TransactionSynchronizationManager.isCurrentTransactionReadOnly()`, wrapped in a `LazyConnectionDataSourceProxy`, since Spring gets the connection before setting that flag.

## JDBC batching

Instead of one round trip per statement, a batch accumulates the parameters of a `PreparedStatement` with `addBatch()`, and sends them all with `executeBatch()`, in one round trip.

```java
String sql = "INSERT INTO book (id, title, author_id) VALUES (?, ?, ?)";

try (Connection connection = dataSource.getConnection()) {
  connection.setAutoCommit(false); // one transaction, not one commit per row

  try (PreparedStatement statement = connection.prepareStatement(sql)) {
    int count = 0;
    for (Book book : books) {
      statement.setLong(1, book.id());
      statement.setString(2, book.title());
      statement.setLong(3, book.authorId());
      statement.addBatch();          // queued, not sent yet

      if (++count % 500 == 0) {
        statement.executeBatch();    // sends 500 rows in one round trip
      }
    }
    statement.executeBatch();        // remaining rows
    connection.commit();
  } catch (SQLException e) {
    connection.rollback();
    throw e;
  }
}
```

- **Batch size**: send by chunks (a few hundred to a few thousand rows) rather than one huge batch, to limit memory on the client and the driver.
- **Auto-commit off**: otherwise each statement is committed separately, which defeats much of the gain; commit once at the end (or per chunk for very large imports).
- **Result**: `executeBatch()` returns an `int[]` with the number of affected rows per statement (`Statement.SUCCESS_NO_INFO` when the driver doesn't know). On failure, a `BatchUpdateException` gives the counts of the statements executed before the error.
- **PostgreSQL**: `reWriteBatchedInserts=true` on the JDBC URL rewrites the batch into multi-row `INSERT ... VALUES (...), (...)`, faster than executing the statements of the batch one by one on the server.

With Spring's `JdbcTemplate`, the loop and the chunking are handled for you:

```java
jdbcTemplate.batchUpdate(
    "INSERT INTO book (id, title, author_id) VALUES (?, ?, ?)",
    books,
    500, // batch size
    (ps, book) -> {
      ps.setLong(1, book.id());
      ps.setString(2, book.title());
      ps.setLong(3, book.authorId());
    });
```

It runs in the current Spring transaction (`@Transactional`), so no manual `setAutoCommit()` / `commit()`.
